# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An interactive Next.js reading of Liu Cixin's *The Three-Body Problem* (**Book I only**). The player picks a character (Ye Wenjie / Wang Miao / Shi Qiang / Mike Evans) and talks to a Claude-driven persona; the app tracks alignment on four ETO ideology axes, forces timeline events on a turn cadence, and can rewind to any earlier decision. Academic final project (Leo & Michael) — see [description.md](description.md).

Two top-level areas:
- `web/` — the Next.js app. **All npm commands run from here**, not the repo root.
- `slides/project-intro/` — presentation artifacts (`index.html` web deck, `.pptx` generated by `create_concise_pptx.ps1` via PowerPoint COM automation on Windows).

## Commands

```bash
cd web && npm install
```

```bash
cd web && npm run dev
```

```bash
cd web && npm run build
```

There is **no test suite and no lint script**. `npm run build` is the de facto verification gate — CONTINUITY.md's Receipts section shows every change historically validated with a build plus an HTTP fetch of the affected route. `playwright` is a devDependency used ad hoc for screenshot/WebGL verification (output lands in `web/.playwright-verify/`), not a configured test runner.

The root `package-lock.json` is an empty stub; it makes Turbopack emit a duplicate-lockfile workspace-root warning on every build. That warning is known and benign.

## Environment

Copy `web/.env.example` to `web/.env.local`. With no `ANTHROPIC_API_KEY`, `/api/chat` returns **mock replies** — the entire UI works, characters just say placeholder text. That mock path is the default development mode; don't assume a key is present.

Model defaults live in [route.ts](web/src/app/api/chat/route.ts): `ANTHROPIC_MODEL` (main persona) and `ANTHROPIC_CLASSIFIER_MODEL` (alignment scorer).

## Architecture

### Persistence: localStorage only, no backend

There is no database and no server-side session. Everything the player does lives in the browser, and the server route is stateless — the client ships its own memory up with every request. Keep it that way unless the user explicitly asks for backend storage (decision D001).

Storage is namespaced per local reader profile via `scopedStorageKey()` in [users.ts](web/src/lib/users.ts) (`tb_user_<id>__<baseKey>`). Loaders fall back to the un-prefixed `legacyStorageKey()` **only** when the current user is `DEFAULT_USER_ID`, so pre-multi-user saves survive. Any new persisted key must go through `scopedStorageKey`.

Three separate stores, easy to confuse:
- [sessions.ts](web/src/lib/sessions.ts) — per-character transcript (`Turn[]`), alignment, compaction state, ending record.
- [shared-memory.ts](web/src/lib/shared-memory.ts) — the **global** cross-character memory and turn counter. This is what makes Shi Qiang know what you told Ye Wenjie.
- [plot-tree.ts](web/src/lib/plot-tree.ts) — flat decision log backing `/decisions` rewind.

Cross-tab and cross-component sync is done with custom window events (`SHARED_MEMORY_UPDATED_EVENT`, `USER_UPDATED_EVENT`) plus the native `storage` event — see `subscribeSharedMemory`.

### The turn loop

Driven by [PlaySurface.tsx](web/src/app/play/[character]/PlaySurface.tsx), which orchestrates every counter below in one `send()` path:

1. Player picks one of three offered choices or types a line.
2. `recordPlayerTurn()` increments the **global** turn (one player message = one global turn, D002) and, every `TIMELINE_TURN_INTERVAL` (10) turns, pops the next entry off `TIMELINE` as a `forcedTimelineEvent` (D003).
3. POST to `/api/chat` with `{ characterId, activeCharacterId, messages, sharedMemory, forcedTimelineEvent, contextCompact, playerTurnCount }`.
4. The route builds a system prompt from cacheable blocks (see below) and fires **two Claude calls in parallel**: the persona reply, and a Haiku alignment classifier scoring the player's last line 0–3 on each axis.
5. Client applies `alignmentDelta`, appends turns, saves the session, and appends to the decision log.
6. Every `CONTEXT_COMPACT_INTERVAL` (5) player turns, `maybeCompactContext()` deterministically summarizes older turns client-side. **Compaction must never increment the story turn** (D005) — it is a separate prompt block, not a turn.
7. When an axis reaches `ENDING_AXIS_THRESHOLD` (7) and at least `ENDING_MIN_TURNS` (6) player turns have passed, the client routes to `/play/[character]/end?axis=...`.

Two counters coexist and are *not* interchangeable: the **global turn** (shared across all characters, drives the timeline) and the **per-conversation player turn** (drives compaction and ending eligibility).

### Prompt assembly and caching

[route.ts](web/src/app/api/chat/route.ts) assembles ordered system blocks: character `systemPrompt` and the rendered World Book both carry `cache_control: ephemeral` (they are the large stable prefix); shared memory, compacted context, and turn state follow uncached because they change every turn. Preserve that ordering when adding blocks — anything volatile placed above the cached blocks defeats the cache.

### The voice contract

Every character prompt in [characters.ts](web/src/lib/characters.ts) ends with `VOICE_FORMAT_RULES`, demanding strict JSON: `{ speech, stage, choices[3] }`. `parseCharacterReply()` extracts the outermost `{...}` and, on any failure, degrades to showing the raw text with generic recovery choices — the UI never deadlocks on a malformed reply. Adding a character means appending to `CHARACTERS` with `systemPrompt` (keep the JSON contract) and `openingScene`.

Characters must **not** emit scene or guest events (D006). Only the forced timeline system creates events; the `guests` and `scenes` fields on `Character` are vestigial. Scene changes belong inside `speech`/`stage` as prose.

### Alignment and endings

[factions.ts](web/src/lib/factions.ts) owns the four axes (adventist / redemptionist / survivor / frontier), the classifier system prompt, thresholds, and per-axis colors. Each character defines a full `endings: Record<Axis, Ending>` — four cinematic endings each — rendered by `EndingView`.

### Chat safety

[chat-safety.ts](web/src/lib/chat-safety.ts) guards the route: body-size cap, message count/length validation, per-instance in-memory rate limit keyed on IP+UA, and demo access code. The key rule (D009): in production, if `ANTHROPIC_API_KEY` is set and `THREE_BODY_PUBLIC_DEMO !== "true"`, the route **fails closed** unless `THREE_BODY_DEMO_ACCESS_CODE` is configured. The browser sends the code via the `x-demo-access-code` header from [DemoAccessCode.tsx](web/src/components/DemoAccessCode.tsx); `demoAccessHeaders()` must be spread into any new client fetch to `/api/chat`. The rate limit is per server instance only — it is not sufficient protection alone on a serverless host.

### Front-page simulation

[ThreeBodyOrbit.tsx](web/src/components/ThreeBodyOrbit.tsx) is a real Three.js velocity-Verlet Newtonian integration ([three-body-physics.ts](web/src/lib/three-body-physics.ts)), not decorative animation, and the user has repeatedly asked that it stay that way (D004). Bodies are small, trails are removed, and damped bounds keep motion in frame.

## Conventions

- **Next.js 16 App Router.** [web/AGENTS.md](web/AGENTS.md) (imported by `web/CLAUDE.md`) warns that this Next version has breaking changes vs. training data — read `web/node_modules/next/dist/docs/` before writing router/route-handler code. Page files stay thin server components that resolve the `[character]` param and hand off to a `"use client"` view component.
- **Styling** is Tailwind v4 with a custom `@theme` palette in [globals.css](web/src/app/globals.css) (`void`, `panel`, `line`, `eto`, `amber`, `parchment`, `trisolaran`, `mute`). Use those tokens, not raw hex or default Tailwind grays.
- **Canon scope is Book I.** Prompts and the World Book must not volunteer Dark Forest deterrence, Wallfacers, or droplets unless the player raises them first.
- **[CONTINUITY.md](CONTINUITY.md) is the project journal** and is actively maintained: dated entries tagged `[USER]` / `[CODE]` / `[TOOL]`, numbered `Dxxx` decisions, a working set, and Receipts recording each verification command and its result. Read it before starting work and update it after substantive changes.
